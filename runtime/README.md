# 운영 증거 원장과 로컬 시제품

기존 `runtime.ledger`와 `runtime.demo`는 **로컬 시뮬레이션**이다. 가상 업무로 중단 복구·의존성·부분 재실행·검수·비용 예약을 시험한다. 실제 봇, 모델, 이미지·영상 생성 도구, 인증 승인 큐, 게시·배포에는 연결되지 않는다.

Python 3.11 이상과 표준 라이브러리를 사용한다. 저장소 루트에서 실행한다.

```bash
python -m unittest discover -s tests -v
python -m runtime.demo --db /tmp/olympus-bam.sqlite
python -m runtime.evaluations examples/evaluation-sample.json
```

문서·계약의 정적 참조 검사는 개발 의존성을 설치한 뒤 실행한다.

```bash
python -m pip install -r requirements-dev.txt
python scripts/validate_contracts.py
```

## 운영 증거 원장 0.1.0

새 `runtime.operations`/`runtime.ops`는 버전·SHA-256을 가진 실제 파일을 확인하고 별도 운영 DB에 기록한다.
시뮬레이션 DB를 운영 DB로 여는 것은 거부한다. 원장 자체는 제작 도구·인증·게시·배포에 연결되지 않는다.

```bash
python -m runtime.ops --help
python scripts/validate_operations.py
python scripts/operations_smoke.py --output /tmp/olympus-file-smoke
```

스모크 출력 디렉터리는 새 경로여야 한다. 모든 예제 업무는 TEST이며 실제 지표에서 제외된다.
[설치·운영 안내](../playbooks/grokbot-process-install.md),
[CLI 입력 계약](../spec/process-cli-v1.json), [운영 적용표](../docs/operations/implementation-status.md)를 따른다.

아래 설명은 기존 시뮬레이션과 오프라인 비교 도구의 범위다. 새 운영 원장은 상위 예산·검수 비용·초과액 정산을
별도로 구현했다. 실측 비교에는 `--require-joint-improvement`를 지정하면 비용과 시간 모두의 개선을 요구한다.

## 1. 밤 업무 원장 데모

`examples/bam-workflow.json`의 가상 업무를 처리한다. 결과는 이미지 파일 대신 `simulation: true`인 메타데이터다. 표정 중 하나의 입력이 바뀌었을 때 해당 단계와 후속 단계만 무효화·재실행하고 다른 표정의 결과와 과거 시도·검수·비용을 보존한다.

같은 `--db` 경로로 다시 실행하면 저장된 상태를 조회한다. 기존 프로젝트를 덮어쓰거나 새로운 실행 비용을 발생시키지 않는다. 새 데모를 만들려면 다른 SQLite 파일 경로를 사용한다. 재시작 당시 해결되지 않은 시도가 있다면 데모는 그 목록을 표시하며 자동 재시도하지 않는다.

예시의 `policy_commit`은 실제 존재하는 v1.2 기준선 커밋이고 `policy_version`도 1.2다. `workflow_version: bam-simulation-v1.3`은 이번 시제품 절차의 버전이다. 배포 전의 v1.3 자기 커밋 해시를 꾸며 넣지 않는다. 이 참조는 정책의 출처 기록이며, 예시가 v1.3 운영 정책을 로드·검증했다는 의미는 아니다. 실제 실행 연결 시에는 실행 정책의 버전과 커밋을 함께 확인해야 한다.

## 2. 지원하는 원장 동작

| 기능 | 로컬 시제품의 동작 |
|---|---|
| 고정 절차 | 순환·중복·없는 의존성·외부 동작을 거부하고 가상 단일 담당자와 검수자를 요구 |
| 준비 상태 | 미완료 선행 단계가 있으면 `DRAFT`, 선행 결과가 독립 검수를 통과하면 `READY` |
| 점유·비용 예약 | SQLite 쓰기 트랜잭션에서 전역 담당자 점유와 프로젝트 동시 작업·총비용을 확인 |
| 검수 | 결과 메타데이터의 필드 유형을 검사하고, 검수 요청의 시도 ID·결과 해시를 현재 결과와 대조한 뒤 지정한 별도 가상 검수자의 판정 후 `DONE` |
| 실패 한도 | 수정본당 최대 2회, 수정 최대 2회, 총시도 최대 6회, 동일 실패 누적 2회 차단 |
| 입력 변경 | 해당 작업·후속 작업만 새 입력 세대로 전환하고 과거 시도·검수·비용·실패 횟수 보존 |
| 진행 중 변경 | 영향을 받는 작업이 실행·검수·결과 불명 상태이면 변경 거부 |
| 중단 복구 | 미완료 상태·비용 예약·점유 보존. 중단 선언과 명시적 결과 대조 후에만 진행 |
| 이력 | 이벤트·검수·실패 레코드의 갱신·삭제를 SQLite 트리거로 거부 |

`cost_units`는 환율이나 실제 결제액을 가정하지 않는 정수 단위다. 결과의 비용은 해당 시도의 예약 상한 이하여야 정산된다. 실제 도구가 예약액을 초과해 청구하는 상황의 전체 정산·사고 처리는 운영 연결 시 구현해야 한다. 독립 검수 자체의 호출 비용도 현재 시제품에는 없으며 운영 계약에서는 총예산에 포함한다.

`Ledger`의 주요 API는 `register_actor`, `create_workflow`, `start`, `stage_result`, `fail`, `review`, `change_input`, `mark_interrupted`, `reconcile`, `snapshot`이다. API의 담당자 ID와 검수 근거 문자열은 로컬 가상 입력이다. 신원 인증·제우스 승인으로 사용할 수 없다. DB 접근 권한이 있는 운영자를 방어하는 변조 방지 저장소도 아니다.

프로젝트 ID와 작업 ID를 다시 등록해 이력을 초기화할 수 없다. 동적 재시도 카드·상위 프로젝트 예산 계층·분산 작업자의 만료 점유 회수는 지원하지 않는다. 동일 목표를 새 프로젝트로 포장하는 의미상의 중복을 시제품이 식별하지도 않는다. 실제 배정 엔진은 공통 예산·작업 계보와 인증 권한을 확인해야 한다.

## 3. 평가 자료와 버전 비교

입력 형식의 전체 예시는 [evaluation-sample.json](../examples/evaluation-sample.json)에 있다. 이 파일의 비용·결과·사람 라벨은 모두 만든 데모 데이터다.

- `dataset`: ID·버전·사례 목록과 목록의 정렬 키·공백 없는 UTF-8 JSON SHA-256.
- `runs`: `baseline` 또는 `candidate`, 과제 ID·시도 번호, 고정한 에이전트·프롬프트·모델·정책·평가자 버전, 환경 ID.
- 결과: 최종 채택·1차 통과 여부, 사람 또는 결정적 검사 결과, 판단 기준 ID, 근거 참조.
- 비용·시간: 실패·재시도·검수까지 포함한 해당 실행의 비용, 완료 소요 시간, 사용자 수정과 예상 밖 개입, 차단 위반 횟수.

비교 쌍은 같은 과제·시도 번호와 환경·정책·평가자·판정 종류·판정 기준 ID를 가져야 한다. 한 버전의 사람 검수와 다른 버전의 파일 규격 검사를 같은 품질 기준으로 비교할 수 없다. 같은 버전 집합 안에서 모델·프롬프트 설정이 섞여도 입력을 거부한다. 데이터셋 내용을 바꾸면 사례 목록 해시도 달라진다.

보고서는 최종 채택률, 1차 검수 통과율, 실패 비용을 포함한 채택 산출물당 비용, 평균 완료 시간, 사용자 수정·개입, 평가자와 사람의 일치·잘못된 통과·반려를 보여준다. 비용은 입력 기록을 집계한다. 실제 결제 기록이나 검수 근거를 외부 시스템에서 인증·수집하는 기능은 없다.

| 권고값 | 의미 |
|---|---|
| `DEMO_ONLY` | 합성 자료. 실제 성과·승격 근거로 사용 불가 |
| `INCONCLUSIVE` | 비교 쌍·표본·범위가 부족해 판단 보류 |
| `KEEP_BASELINE` | 개별 과제의 품질 회귀·차단 위반·개입 증가·개선 부재 등을 검토해야 함 |
| `CANDIDATE_FOR_REVIEW` | 표본에서 개선 관찰. 독립 검토 대상으로 올릴 수 있으며 자동 적용 허가는 아님 |

기본 최소 표본은 20쌍이며 `--minimum-pairs`로 조정한다. 이는 초기 검토를 위한 설정값으로 통계적 우월성이나 반복 신뢰성을 보증하지 않는다. 사례 수와 시도 수를 따로 보고하며, 비용·시간·품질의 상충 결과와 실제 사용 범위는 독립 검토에서 판단한다. 기준 버전에 차단 위반이 있다면 `KEEP_BASELINE`을 계속 운영하라는 승인으로 해석하지 않고 기존 버전도 별도 점검한다.

평가의 `version_promoted`는 항상 `false`다. 실제 기억 승격·버전 적용·되돌리기는 [운영 플레이북](../playbooks/agent-operations.md)의 절차와 승인 범위를 따라 별도로 구현한다.

## 4. 검증의 범위

단위 테스트는 가상 작업을 사용해 저장·재시작·동시 접근·비용·독립 검수·입력 변경·실패 한도와 평가 비교를 확인한다. 합성 테스트 통과는 실제 밤 원형 승인, 인간 등록, 모델 품질 평가, 수동 종단간 검증 2회에 포함되지 않는다.

`scripts/validate_contracts.py`는 저장소의 YAML과 문서·슬롯·템플릿 참조를 검사한다. 운영 요청마다 권한과 모든 정책을 강제하는 프로덕션 정책 엔진은 아니다.
