# GitHub·Notion·Craft 도구 사용 Process

버전 0.1.0 / 헌법 v1.3 OLY-OPS-001..006 적용 지침.
목표는 자료를 다시 찾는 시간, 중복 입력, 오래된 정보로 인한 재작업, 도구 호출 실패를 줄이는 것이다.
아래 도구별 역할은 운영 적용안이다. 이 문서 추가만으로 외부 DB·동기화·자동화를 설치하지 않는다.

## 1. 정보마다 기준 원본을 정한다

| 정보 | 기준 원본 | 다른 도구에 남기는 내용 | 갱신 책임 |
|---|---|---|---|
| 헌법·Skill·템플릿·코드 | GitHub의 검토된 커밋 | 버전·커밋 링크·변경 요약 | 담당 신의 제안 → 기존 검토 절차 |
| 코드·정책 개선 요청 | GitHub Issue | 업무 ID·이슈 링크·요약 | 헤스티아가 범위와 완료 조건 관리 |
| 사업 목표·우선순위·기획 결정 | 비공개 Notion 프로젝트 | 결정 ID·관련 업무 링크 | 제우스의 의도에 따라 헤스티아가 정리 |
| 실행 상태·점유·시도·비용·검수 결과 | 비공개 운영 원장 | Notion에 관측 상태·근거·관측 시각 표시 | 실행·검수 담당자가 원장에 기록 |
| 원본 이미지·영상·코드 산출물·승인 근거 | 비공개 자산 저장소·실행 원본 시스템 | 자산 ID·버전·해시·접근 가능한 링크 | 제작·검수 담당자 |
| 아이디어·메모·초안·회고 후보 | 사용 중인 Craft 또는 Notion 메모 | 채택 시 프로젝트/결정/이슈 링크 | 작성자, 채택은 헤스티아 |
| 실제 Bot·루틴·도구 설정 | 현재 Grokbot 설정과 복구용 export | Notion 구성표에 수집 시각과 출처 | 헤스티아가 현재 값과 대조 |

Craft는 현재 쓰는 메모·초안 흐름을 살리는 선택 경로다. 모든 업무가 Craft·Notion·GitHub를 모두 거칠 필요는 없다.
콘텐츠 한 편의 제작에는 비공개 업무 ID만으로 충분할 수 있다. 코드·정책·절차 변경이 발생할 때 GitHub Issue를 연결한다.
Notion 화면에서 완료를 선택해도 원장의 실행 완료로 역전파하지 않는다. 사용자 변경 요청은 별도 요청 필드로 접수한다.

## 2. 하나의 업무를 끝까지 연결한다

예시: 블로그 메모 → 원고·이미지 제작 → 게시 준비 → 회고.

1. Craft/Notion에서 메모를 찾는다. 이미 채택한 메모이면 연결된 프로젝트로 간다.
2. 헤스티아가 Notion에 목표·성공 기준·우선순위를 정리하고 공통 project_id/task_id를 배정한다.
3. 코드나 절차 수정이 필요하면 기존 GitHub Issue를 먼저 찾는다. 없을 때만 새 이슈를 만들고 같은 ID를 적는다.
4. GitHub의 고정한 Skill 버전과 비공개 입력 자산으로 원장 create/claim을 수행한다.
5. 원고·이미지·출처 파일을 제출하고 별도 검수자가 검수한다. Notion은 원장의 상태와 검수 근거를 보여준다.
6. PR 병합은 코드 반영 상태만 갱신한다. 실제 적용·게시·운영 수용은 각각 증거가 있어야 완료로 바꾼다.
7. 헤스티아가 결과와 가장 큰 병목 하나를 정리한다. 검증된 절차 개선은 GitHub, 원시 회고는 메모에 남긴다.

동일 업무 ID를 외부 도구의 object_id와 매핑한다. 이름으로 연결하지 않는다.
한 업무당 같은 도구의 관리 객체는 원칙적으로 하나다. 다중 산출물·여러 PR이 필요하면 역할을 구분한 링크 목록으로 둔다.

GitHub는 이슈와 PR 연결 및 병합 시 자동 종료를 지원한다.
운영 검증까지 필요한 상위 이슈는 일반 참조로 연결하고 코드 병합만으로 닫히는 연결을 만들지 않는다.
[GitHub 공식 문서](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## 3. 도구 호출은 찾기 → 읽기 → 수행 → 다시 읽기로 통일한다

- **목적 확정:** 이번 호출로 결정할 내용 또는 바꿀 필드 하나를 정한다.
- **연결 확인:** workspace/repository/페이지 범위와 가능한 읽기·쓰기 기능을 확인한다.
  도구 목록에 있다는 사실과 실제 호출 성공을 구분한다.
- **찾기:** 저장한 object_id/URL이 있으면 직접 조회한다. 없을 때만 해당 프로젝트·날짜 범위에서 검색한다.
  제목·발췌는 발견용이다. 정책·승인·실행 판정에는 원문을 읽는다.
- **읽기:** 원본 버전·수정 시각·해시·현재 상태를 확인한다. 관련 없는 전체 대화를 반복해서 읽지 않는다.
- **수행:** 연결 도구/API/CLI를 우선한다. 같은 대상의 쓰기는 직렬 처리하고 필요한 필드만 바꾼다.
  UI는 필요한 기능이 직접 인터페이스에 없을 때 사용한다. UI와 API에서 같은 변경을 중복 실행하지 않는다.
- **다시 읽기:** 반환된 object_id로 실제 저장 필드·본문·링크를 확인한다.
  HTTP 성공, “생성 완료” 메시지, 문서 제목만으로 인계를 완료하지 않는다.
- **기록:** 요청 목적·대상·전후 버전·결과·오류 분류·확인 증거를 업무 ID에 연결한다.

독립적인 읽기는 병행할 수 있다. 원장 배정·예산·검수 제한은 도구 호출 중에도 유지한다.
읽기/쓰기별 대상 권한과 사용자가 이미 허용한 범위를 따른다. 정상적인 내부 기록마다 사용자에게 재승인을 요구하지 않는다.

실행 기록 예시는 [도구 호출·인계 기록](../templates/tool-operation.example.yaml)에 있다.
템플릿은 기록 형식이며 현재 CLI의 새 명령이나 인증 토큰이 아니다.

## 4. Notion을 한눈에 보는 작업 화면으로 만든다

기존 데이터베이스에 대응 필드가 있으면 확장한다. 같은 목적의 DB가 있는지 먼저 확인한다.
최소 구성은 프로젝트와 업무 현황이다. 자산이 여러 작업에서 재사용될 때 자산 목록을 추가한다.

| 목록 | 핵심 필드 | 추천 보기 |
|---|---|---|
| 프로젝트 | project_id, 목표, 라인, 우선순위, 결정 담당, 관련 이슈, 정책/Skill 버전 | 라인별 진행·완료 기준 미확정 |
| 업무 현황 | task_id, 프로젝트 관계, 담당자, 관측 상태, 다음 행동, 차단 사유, 검수자, 근거 링크, source_revision, observed_at, sync_status | 검수 대기·차단·사용자 선택 필요·오래된 상태 |
| 자산 | asset_id, 버전, 해시, 저장소 링크, 검수 참조, 사용 프로젝트 | 승인 원형·재사용 가능·갱신 영향 있음 |

프로젝트와 업무·자산은 관계로 연결하고 집계는 연결된 자료에서 만든다.
[Notion 관계·롤업 공식 문서](https://www.notion.com/help/relations-and-rollups)

관측 상태와 사용자의 요청 상태를 다른 필드로 둔다. 예를 들어 observed_state=REVIEW,
requested_action=범위 수정 요청은 함께 존재할 수 있다. 원장의 상태는 직접 바꾸지 않는다.
원장 자동 반영이 아직 없으면 MANUAL_SNAPSHOT과 관측 시각을 표시한다.

## 5. 동기화와 충돌을 관리한다

- 갱신 시점: 요청 확정, 담당 변경, 제출, 검수, 차단, 결과 대조, 입력 버전 변경, 실제 실행 확인.
- 갱신 내용: 바뀐 상태·다음 행동·근거 링크·원본 버전. 전체 문서 복사와 상시 전수 검색을 줄인다.
- 문서의 사람 작성 영역과 관리 도구가 갱신하는 필드를 구분한다.
- source_revision이 이전 관측보다 오래되면 덮어쓰지 않는다. 버전이 순서형이 아니면 원본을 다시 읽어 현재 값을 대조한다.
- 읽은 뒤 대상이 바뀌었으면 변경 필드를 다시 비교한다. 조건부 갱신 기능이 없는 연결은 단일 쓰기 담당자와 재조회로 충돌을 줄인다.
- 실패는 PENDING/STALE/CONFLICT/UNAVAILABLE로 남긴다. 최신 성공 시각을 현재 시각으로 바꾸지 않는다.
- 응답이 끊긴 쓰기는 대상과 고유 키를 조회해 성공 여부를 대조한다. 확인 전 새 페이지·이슈를 재생성하지 않는다.
- 401/403은 연결·권한, 404는 대상/범위/연결 endpoint, 429는 호출 제한, timeout/5xx는 결과 불명으로 분류한다.
  404만으로 문서 삭제나 서비스 전체 장애를 단정하지 않는다. 기존 시도 상한을 다른 도구로 우회하지 않는다.

첫 적용은 명시적인 수동 갱신과 읽기 확인으로 검증한다. 반복 성공한 좁은 구간만 자동화 후보로 올린다.
웹훅을 사용하려면 접근 가능한 수신 서비스·권한·검증·실패 복구를 별도로 구성해야 한다.
Notion 웹훅은 변경 알림의 ID로 원본을 다시 조회하는 흐름을 지원한다. 이 패키지는 해당 구독을 설치하지 않았다.
[Notion 웹훅 공식 문서](https://developers.notion.com/reference/webhooks)

## 6. 내보내기 인계의 완료 조건

원격 컴퓨터 경로와 해시만 받으면 “원본 위치를 보고받음”이다.
수신자가 그 경로를 읽을 수 없으면 자료 인계는 아직 끝나지 않았다.

1. 송신자는 원본 JSON과 항목 수를 보존한다. 표시용 요약과 전체 자료를 명확히 구분한다.
2. 수신 연결로 읽을 수 있는 JSON 본문 또는 비공개 파일을 제공한다. 빈 코드 블록을 완료본으로 보내지 않는다.
3. 본문이 잘리면 실제 연결에서 검증한 크기로 분할한다. 각 부분에 export_id·part 번호·총 부분 수·바이트 해시를 둔다.
4. 분할 전 원본 바이트를 손실 없이 복원한 뒤 전체 해시와 bots/routines/runs 수를 대조한다.
   요약본을 이어 붙여 원본 해시를 맞췄다고 보고하지 않는다. 현재 bridge는 완성된 JSON 한 파일만 받는다.
5. 수신자가 JSON 파싱·필수 목록·중복·해시/항목 수 대조 결과를 확인한 후 ACKNOWLEDGED로 기록한다.
6. 증거의 전송 완료와 실제 Bot 적용·실행 검증 완료는 별도로 기록한다.

원본 파일 바이트 SHA-256과 bridge가 출력하는 정규화 JSON source_sha256은 서로 다른 해시다.
원본 전송 무결성은 원본 바이트 해시로 확인한다. 공백·키 순서를 바꾼 뒤 같은 바이트 해시라고 주장하지 않는다.

## 7. 실제 적용 순서와 측정

먼저 기존 GitHub 이슈·Notion 문서 하나를 업무 ID로 연결하고 원문 찾기, 필드 갱신, 읽기 확인을 시험한다.
다음으로 원장 제출→Notion 검수 대기 표시→독립 검수→표시 갱신을 실제 업무 하나에서 검증한다.
Craft는 연결을 확인한 후 메모 채택→프로젝트 링크 기록을 시험한다. 연결이 안 되면 Notion 또는 비공개 파일 export를 사용한다.

도구별로 다음을 실제 기록에서 측정한다: 필요한 자료 발견 시간, 업무당 조회/쓰기 횟수,
첫 호출 성공률, 중복 객체 수, 오래된 상태 지속 시간, 인계 ACK 성공률, 수동 복사 횟수.
호출 수 감소만으로 개선이라 판정하지 않는다. 누락·잘못된 완료·사람 수정이 증가하지 않아야 한다.
기준 자료가 없으면 UNMEASURED다. 반복 실행 자동화는 기존 운영 수용·승인 조건을 따른다.
