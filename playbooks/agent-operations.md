# OLYMPUS 실행·평가·개선 운영 플레이북

- 적용 기준: [v1.3 헌법](../OLYMPUS_Agent_Architecture_v1.3.md) 27장과 [운영 계약](../spec/operations-v1.yaml).
- 반영 단계: `DOCUMENTED`. 로컬 코드 상태: `LOCAL_SIMULATION_ONLY`.
- 적용 범위: 다섯 프로젝트 라인의 내부 실행·검수·회고. 현재 89개 슬롯과 인간의 직무·이름·삭제 금지 규칙을 유지한다.

## 1. 현재 가능한 일과 생산 연결의 차이

현재 `runtime/ledger.py`는 SQLite에 가상 업무·상태·결과 메타데이터를 저장하고 재시작·제약·입력 변경을 시험한다. `runtime/evaluations.py`는 고정된 비교 자료를 집계한다. 실제 모델·도구를 호출하거나 그림·동영상을 만들지 않는다. 인증된 승인 큐, 생산용 라우팅, 예약, 게시, 기억 검색·자동 버전 적용은 연결되지 않았다.

```bash
python -m runtime.demo --db /tmp/olympus-bam.sqlite
python -m runtime.evaluations examples/evaluation-sample.json
```

오프라인 평가의 합성 자료는 항상 `DEMO_ONLY`이며, 실제 자료라도 표본·쌍별 결과가 부족하면 `INCONCLUSIVE`다. `CANDIDATE_FOR_REVIEW`는 검토 후보이지 자동 적용 결정이 아니다. CLI의 기본 최소 20쌍은 변경 가능한 사전 검토 기준이며 통계적 확신이나 모든 직무의 공통 최소치를 뜻하지 않는다.

실행 방법과 지원 범위의 상세는 [런타임 안내](../runtime/README.md)를 따른다. 예시의 가상 담당자와 검수 결과는 `registry/humans.yaml` 등록, 제우스 원형 승인, 실제 수동 종단간 검증 2회에 해당하지 않는다. `cost_units`는 예시의 정수 비용 단위이며 실제 결제액이 아니다. 실제 성과 자료를 확보하기 전에는 절감률이나 품질 향상을 보고하지 않는다.

## 2. 첫 요청에서 실행 절차 확정 (`OLY-OPS-001`)

1. 헤스티아가 목표·범위·현재 정책·완료 조건과 총예산을 정한다. 새 프로젝트가 기존 상위 목표의 일부면 동일 상위 예산 ID에 연결한다.
2. 필요한 신만 선택하고 DAG를 만든다. 각 단계에는 단일 직무 슬롯, 입출력 계약, 선행 단계, 실행 템플릿 버전, 검수·승인 지점이 있다. 해당 신이 기존 인간을 검색·선택한다.
3. 워크플로 ID·버전·해시를 확정한다. 입력과 모델·템플릿·기억·현재 원형 등 결과에 영향을 주는 의존성을 빠짐없이 고정한다.
4. 같은 최종 버전의 실제 수동 종단간 검수 통과 2회를 확보하면 헤스티아가 `VALIDATED`로 등록할 수 있다. 단위 테스트·가상 자료는 합산하지 않는다.
5. 이후 요청에서는 입력·정책·권한이 맞는 검증 버전을 선택한다. 실행기는 고정 절차를 진행하고 계획 밖 상황만 헤스티아에게 반환한다. 단계 생략·권한 확대·신규 인간 생성 판단을 실행기가 임의로 하지 않는다.

검증된 워크플로도 첫 실행과 새 입력의 내용은 다를 수 있다. 검수·현재 원형·예산·정확한 공개 매니페스트 승인을 매번 확인한다. 예약 활성화는 별도 [루틴 규칙](../OLYMPUS_Agent_Architecture_v1.3.md#201-루틴-예약-활성화-oly-rtn-001)을 따른다.

## 3. 실행 전에 자원 확보 (`OLY-OPS-006`)

`READY`는 실행 권한 획득이 아니다. 배정 트랜잭션에서 인간의 전역 점유, 각 상위 프로젝트의 동시 실행 상한, 작업의 누적 실패 한도와 비용 예약을 함께 확보한다. 어느 하나가 부족하면 `READY`에서 사유를 남기고 기다린다.

| 원인 | 다음 동작 |
|---|---|
| 같은 인간이 다른 작업을 수행 중 | 기존 점유 종료 확인 후 재배정 |
| 프로젝트 실행 상한 도달 | 실행 완료·정산 이벤트 후 재평가 |
| 검수 대기 상한 도달 | 새 제작은 보류하고 확보한 검수 여유·예산으로 검수 진행 |
| 비용 추정 누락·잔액 부족 | 실행 보류, 헤스티아가 범위·방법·기존 승인 한도 판단 |
| 원격 결과 불명 | 비용 예약·점유 유지, 대조 완료 전 재시도 금지 |

정수 비용 단위는 실행 전 정하고 모든 비교에 동일하게 쓴다. 제작·검수·실패·수정·실험 비용을 모두 총한도에서 처리한다. 실제 초과 비용도 숨기지 않고 정산하며 신규 배정을 중단한다. 상위 예산을 하위 프로젝트나 새 카드로 우회하지 않는다. 생산용 상위 프로젝트 예산 계층·독립 검수 용량은 구현·검증이 추가로 필요하다.

## 4. 중단과 입력 변경 처리 (`OLY-OPS-002`)

완료 체크포인트에는 입력·결과 해시, 담당자와 점유 세대, 워크플로·정책·템플릿·모델·기억 버전, 검수, 비용과 누적 실패가 있다. 프로세스가 재시작해도 결과 파일·해시·현재 정책과 원형·현재 유효성을 확인한 뒤 재사용한다.

입력이 바뀌면 헤스티아는 직접 소비 단계와 후속 단계를 찾는다. 원래 작업·완료 결과는 보존하고 현재 결과 참조를 무효화한 뒤 새 수정본을 만든다. 변경된 작업 계보의 누적 실패·수정·비용을 이어받는다. 공통 원형이나 정책 변경은 모든 관련 단계의 영향 검토 대상이다.

| 밤 작업에서 바뀐 것 | 다시 검토하거나 수행할 범위 | 재사용 조건 |
|---|---|---|
| ‘당황한 밤’ 제작 지시 | 해당 표정 제작·검수, 이를 사용하는 동작, 최종 묶음 | 다른 5개 표정의 입력·원형·정책·검수 결과가 여전히 유효 |
| 동작의 길이 | 해당 동작과 최종 패키지·매체 검수 | 입력 정지 이미지가 그대로이며 검수·원형 조건 충족 |
| 공통 원형의 잎·얼굴 규칙 | 해당 원형을 쓰는 모든 파생·소비 단계 영향 검토 | 기존 원형 재사용은 `OLY-CHR-001`의 명시적 예외 절차 필요 |
| 공개 제목·설명·시각 | 최종 실행 매니페스트 검수와 새 공개 승인 | 내용이 동일한 제작 자산만 별도 재사용 가능 |

로컬 예시는 영향을 받는 단계가 실행 중이면 입력 변경을 거절한다. 생산 구현에서는 배정 정지·작업자 중단 또는 종료 확인·외부 실행 대조 후 새 세대를 시작해야 한다. 이전 세대의 늦은 응답은 현재 결과로 올리지 않는다. 이미 공개된 자산은 이력 보존 후 별도 승인된 변경으로 처리한다.

## 5. 실제 평가 자료 축적 (`OLY-OPS-003`)

데메테르는 최종 결과만 아니라 첫 검수, 반려 사유, 수정본, 미완료 작업과 비용도 수집한다. 헤라는 실제 사용자 결정 또는 독립 검수로 라벨을 확인한다. 제작자의 자기 평가는 참고이며 독립 정답이 아니다.

각 평가 사례에는 데이터셋·버전, 작업 범위, 입력·결과 참조, 실제/합성 구분, 라벨 작성자·검증자·근거, 평가 기준 버전이 필요하다. 개인·프로젝트 자료는 접근 범위를 지켜 사용한다. 판정 충돌·필수 필드 누락은 제외 수와 사유를 보고하고 검증 전 정답으로 쓰지 않는다.

헤라는 평가자 판정과 확인된 라벨을 비교해 잘못된 통과·반려, 불일치 원인을 정리한다. 스키마·규격·필수 테스트·승인 위반은 코드 차단 조건으로 유지한다. 기존 80점 기준은 실제 자료로 적합성을 확인하기 전 임의 조정하지 않는다.

| 지표 | 정의와 주의점 |
|---|---|
| 1차 검수 통과율 | 첫 검수 통과 산출물 / 첫 검수를 받은 산출물. 검수 전 중단은 별도 집계 |
| 최종 채택 산출물당 비용 | 실패·중단·수정·검수를 포함한 프로젝트 총비용 / 최종 채택 산출물 수. 0개면 단가 미정 |
| 완료 시간 | 요청부터 최종 채택까지. 실행·승인·검수 대기를 구분하고 미완료는 미완료로 표시 |
| 사용자 수정 횟수 | 사용자 변경 요청 이벤트 수. 품질 수정과 범위 변경을 구분 |
| 검수 대기시간 | 제출부터 검수 시작까지 |

모든 지표에 기간·분모·표본 수·작업 범위·통화 또는 시뮬레이션 단위를 표시한다. 초기 소표본과 합성 결과를 실제 운영의 일반적 개선으로 보고하지 않는다.

## 6. 회고를 검증된 기억으로 만들기 (`OLY-OPS-004`)

1. 데메테르가 반복되는 문제와 근거를 `PROPOSED` 레코드로 작성한다. 예: “이 도구 버전에서 작은 잎이 동작 중 변형된 사례가 있었다”처럼 조건과 관찰을 적는다.
2. 해당 신이 프로젝트·슬롯·모델·템플릿·원형 등의 적용 범위를 정하고 독립 검증자가 근거를 확인한다. 품질 기준은 헤라가 검수하고 쓰기 권한은 헤스티아가 검증한다.
3. 기억 ID·버전, 사실/절차/선호/가설 유형, 책임 신·검증자·근거·유효기간·이전 버전 참조를 갖춘 뒤 `ACTIVE`로 등록한다. 범위와 권한이 맞는 업무에만 주입하고 참조 버전을 기록한다.
4. 반례·만료·모델/원형 변경 시 `EXPIRED`, `REVOKED`, `SUPERSEDED` 등으로 처리하고 영향 업무를 찾는다. 기록을 지우지 않는다.

원형 승인·헌법·제우스의 명시적 결정을 기억이 덮어쓸 수 없다. 현재 로컬 원장에는 운영 기억 검색·검증·철회 적용이 구현되지 않았다. 이 절차를 구현하기 전 피드백 수집을 자동 학습 완료로 보고하지 않는다.

## 7. 버전 변경 비교와 되돌리기 (`OLY-OPS-005`)

후보 프롬프트·템플릿·모델이 생기면 해당 신은 변경점과 적용 범위를 제안한다. 비교 전에 표본 최소치·범위, 품질·비용·시간 기준, 차단·중단 조건과 롤백 대상을 등록한다. 표본 최소치는 업무 특성에 맞게 정하며 예시 숫자를 보편 기준으로 삼지 않는다.

기준·후보를 같은 입력 집합과 라벨·검수 기준으로 비교한다. 실제 결과 누락이나 조건 차이를 표시한다. 모델 설정·기억 스냅샷·도구 권한까지 고정하거나 변경 사실을 명시한다. 평가 기준을 고친 자료는 별도 비교 자료와 분리한다.

증거 부족·합성 자료만 존재·라벨 미검증·짝이 맞지 않는 결과·사전 기준 없는 상충 결과는 `INCONCLUSIVE`다. 오프라인 평가의 적격 판정도 자동 적용 허가가 아니다. 헤라 검수 후 해당 신이 제한 범위를 제안하고 헤스티아가 새 업무부터 배정한다. 정책·권한 확대는 기존 제우스 승인 규칙을 따른다.

후보가 중단 조건을 충족하면 새 배정을 멈추고 현재 정책·원형과 호환되는 이전 버전으로 되돌린다. 진행 중 작업의 버전은 조용히 바꾸지 않는다. 인간의 ID·직무·이름·과거 프롬프트와 이력은 유지한다.

## 8. 밤 파일럿의 시작 조건

가장 작은 실제 파일럿은 기본 원형 확정, 표정 6종, 개발자밤 동작 한 개다. 실제 시작에는 밤 설정의 원형 후보를 검수·승인하고, 참조 파일 접근·해시 확인, 직무별 인간 등록·완전한 템플릿·모델과 도구 권한·예산, 검수자를 준비해야 한다. 현재 저장소의 후보 원형과 빈 인간 레지스트리를 승인·등록 완료로 간주하지 않는다.

순서는 로컬 메타데이터 예시 → 생산 연결·실제 파일럿 → 실측 평가 자료 → 제한 적용이다. 수동 성공 사례가 쌓이기 전 자동 예약하지 않는다. 첫 회고에서는 지표의 관측값·표본 수, 병목과 다음 한 가지 수정만 정리한다. 실제 성과가 없으면 미측정으로 남긴다.
